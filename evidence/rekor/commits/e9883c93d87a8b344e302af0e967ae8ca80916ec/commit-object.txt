fix: preserve a "__proto__" key when rebuilding JSON trees

Two places rebuild a JSON-derived object by assigning onto a fresh `{}`:
resolveArgs (exec-engine.ts) for outgoing tool arguments, and pruneJson
(prune.ts) for incoming upstream results.

JSON.parse produces "__proto__" as an OWN data property, but `out[k] = v`
does not create an own key for it -- it invokes Object.prototype's
__proto__ setter. The rebuilt object therefore has no own "__proto__", and
since JSON.stringify only serializes own properties the field is silently
dropped: an exec step loses an argument it declared, and a pruned tool
result loses a field the upstream server actually returned.

To be clear about what this is NOT: Object.prototype is never touched, so
this is not prototype pollution. Only the freshly constructed object's own
prototype is affected, and the observable consequence is a dropped field.

Assign via Object.defineProperty for that one key so it lands as the plain
data property the input had. The common path keeps plain assignment, so
there is no cost on ordinary keys.

Adds 6 tests. All of them fail before this change (3 in exec-engine, 1 in
prune) and pass after; the remainder pin that Object.prototype stays clean
and that $ref resolution still works inside a __proto__-keyed argument.

Note for reviewers: the tests build their expected values with JSON.parse
rather than object literals, because `{ __proto__: ... }` in source sets
the prototype instead of creating an own key -- the same trap the fix is
about, and one an assertion can silently fall into.
