fix(oam): bound the `oam --version` probe with a timeout

probeOam() calls execFileSync with no timeout. execFileSync blocks the
event loop, and this sits on the upstream connect path of a single-threaded
broker, so an oam binary that hangs rather than exiting -- stuck on a
network mount, a wedged FUSE path, a process stopped under a debugger --
takes the entire hub down with it. The client stdio transport and every
in-flight upstream call stop being serviced, and there is no way to break
out because nothing is watching the clock.

Add `timeout: 3000`, matching the budget uv-bootstrap's onPath() probe
already uses for the same "is this binary here and working" question.

On timeout execFileSync throws, which the existing catch already turns into
`{ bin: null }` -- the same result as oam being absent -- so the server
falls back to node/npx. The worst case becomes a bounded 3s stall followed
by the documented fallback, instead of an unbounded hang. The probe result
is cached, so this is paid at most once per process.

Scope: only servers whose effective runtime is "oam" reach this
(connectToUpstreamOnce gates on it), but YAW_MCP_DEFAULT_RUNTIME=oam turns
that on for every local server at once.

Adds 3 tests: the constant, that a throwing probe degrades to the
node-fallback shape, and that an opted-in npx server keeps its original
command after a timed-out probe.
